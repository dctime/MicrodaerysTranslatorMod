## Q1：三個常數合不合理

我用**你自己量到的延遲**當尺：Groq 0.3–0.6s、Google 0.6–2.4s、OpenRouter 5.6–6.6s、NVIDIA 9.5–15s。

### `NEUTRAL_UNTRIED_PENALTY = 0.3` — **選得好**

0.3 × `LATENCY_FULL_PENALTY_MS` = 等效 1.5 秒。對照你的資料：比 Groq 差、跟 Google 差不多、比 OpenRouter/NVIDIA 好。

**這正是一個未知 provider 應該待的位置**——不會把已證明很快的 Groq 擠掉，但只要 Groq 忙或額度滿就會被探索到。而且你在註解裡明說它「跟真實 latencyPenalty 是同一個尺度、不是另一套分數」，這點很重要，因為兩個不同尺度的數字相加是這類公式最常見的無聲錯誤。**這個常數我沒有意見。**

### `LATENCY_FULL_PENALTY_MS = 5000` — **你沒問，但它才是問題所在**

```java
double rawPenalty = clamp01(averageLatencyMs / LATENCY_FULL_PENALTY_MS);
```

**5 秒以上一律 1.0。** 所以在這個公式眼裡：

- OpenRouter（6s）= 1.0
- NVIDIA（15s）= 1.0
- **兩者完全無法區分。**

你自己量到的範圍是 0.3s 到 15s（50 倍），而這個常數把**上半段整個丟掉**。結果是 scorer 沒有能力偏好「慢但還能用」勝過「慢到不能用」——而那正好是你那份 log 裡最需要區分的兩家。

**建議把它拉到你實測範圍的上緣**（例如 10000–15000），或者改用對數尺度。5000 這個數字在只有 Google/Mistral/Ollama 三家的世界裡合理，在 11 家、實測跨 50 倍的世界裡就不夠用了。

### `STALENESS_MAX_DISCOUNT = 0.7` — **我會調小，理由是一個原則**

一個已證明很爛的 provider（rawPenalty = 1.0）放置 5 分鐘後：`1.0 × (1 − 0.7)` = **0.3**。

而 `NEUTRAL_UNTRIED_PENALTY` 也是 **0.3**。

**也就是說：「我們量到你要 15 秒」最後會收斂到跟「我們對你一無所知」完全相同的分數。**

我建議的原則是：**有資訊，永遠不該讓一個 provider 看起來比沒資訊更好。** 我們對 NVIDIA 有正面證據說它很慢；那個證據就算打折，也不該打到跟「從沒試過」平手。把上限調到 0.5 左右（衰減底線 0.5 > 0.3）就能維持「會定期重新探索」的原意，同時保住「我們知道它爛」這個資訊。

### `STALENESS_FULL_RECOVERY_MS = 5 分鐘` — 數字可以，但代價要講明

這個常數實際控制的是**探索的頻率**，而探索的代價在這個 mod 裡是**玩家看得見的**：重新探索 NVIDIA 一次 = 一個 tooltip 等 15 秒（`TIMEOUT_DURATION_CONFIG` 預設 30s，所以不會 timeout，就是純等）。

5 分鐘我覺得可以接受，但**請在完成報告裡用這個說法寫**：「每個表現不佳的 provider，大約每 5 分鐘會被重新試一次，那一次翻譯會慢」。這樣使用者才知道自己在買什麼——而不是之後回報「偶爾會突然很慢一次」時沒人想得起來是這個機制。

## Q2：「debuggable，不是黑盒」還站得住嗎

**程式碼層面：站得住。** 我讀了，分支是 4 行、沒有隱藏狀態、沒有隨機、同樣輸入必定同樣輸出，而且你把兩個機制設計成互斥（`hasLatencySample == false` 就完全不看 staleness），沒有交互作用要推理。以「能不能逐行讀懂」這個標準，承諾成立。

**但實務層面：不站得住，而原因在 UI 不在公式。**

我查了 Provider Detail 那個 Status 行實際有的 lang key：`ready` / `rate_limited` / `cooldown` / `invalid_key` / `cannot_connect` / `disabled`。

**`hasLatencySample` 跟 `millisSinceLastAttempt` 這兩個新輸入，在整個 UI 裡沒有任何地方看得到。**

所以「為什麼 AUTOMATIC 剛剛選了 NVIDIA？」這個問題，現在的答案取決於兩個**沒有人能觀察到**的變數。一個公式可以逐行讀懂，但如果它的輸入看不見，實際除錯時它跟黑盒沒有差別——你只能去讀 code 反推，那正是「不是黑盒」這個承諾想避免的事。

**建議（成本很低）：** Status 行本來就每 tick 更新了。多顯示兩個欄位——平均延遲、上次使用距今多久（沒資料時顯示「未試過」）。這兩個字串加上去，公式的兩個新輸入就變成可觀察的，承諾才真的落地。而且對使用者也有價值：他問「有時候蠻久才翻譯」的時候，如果當時能打開 Provider Detail 看到「NVIDIA 平均 12.3 秒」，這一整輪的診斷可能根本不需要你去量。

## 一個順帶的觀察：`priorityBias` 的量級

`priorityBias = (priority − 1) × 0.05`，priority 範圍 1–11 → **0 到 0.5**。

而 latencyPenalty 的範圍是 0 到 1。所以 priority 的跨度是延遲跨度的一半——**在一群都「夠快」的 provider 之間（penalty 全都在 0.06–0.48），priority 是壓倒性的**。

這大概就是 priority 該有的作用，我不認為是缺陷。**但 class javadoc 那句「priority is a nudge, not an override」值得補一個範圍**：它相對於「失敗、額度用盡、5 秒以上的延遲」是 nudge，相對於「健康 provider 之間的延遲差異」其實是主導因素。現在那句話讀起來像是無條件的。

## 我可能錯的地方

**這些全部是常數之間相對關係的結構分析，不是實證調參。** 我沒有任何資料說明 1.5 秒的中性值在真實遊玩中會產生好的行為——只有一次長時間 AUTOMATIC 遊玩才知道。

**唯一我有把握的是那兩個「巧合的相等」**：5 秒的 clamp 讓 6s 跟 15s 變成同一個數字、0.7 的折扣讓「量過很爛」跟「沒量過」變成同一個數字。這兩個不需要實測就能判斷是不是你要的——**如果是刻意的，那沒問題；如果是常數各自選出來之後才碰巧相等的，那值得再看一眼。**
